# 요구사항

## 0. 단어

### 라이브러리와 프레임워크 비교
---
| 구분 | 라이브러리 | 프레임워크 |
|---|---|---|
| 기본 개념 | 필요한 기능을 가져다 사용 | 애플리케이션의 기본 구조를 제공 |
| 제어권 | 개발자 | 프레임워크 |
| 호출 방향 | 내 코드 → 라이브러리 | 프레임워크 → 내 코드 |
| 프로그램 구조 | 내가 자유롭게 구성 | 프레임워크가 어느 정도 결정 |
| 사용 방법 | 필요한 기능만 선택해서 사용 | 정해진 규칙과 구조를 따르는 경우가 많음 |
| 대표 예시 | STL, Boost, OpenSSL | Spring, Django, ASP.NET Core |
| 핵심 개념 | 기능 재사용 | 애플리케이션 구조 + 실행 흐름 |

- ORM
    - Object-Relational Mapping, 객체 관계형 매핑
    - 객체와 관계형 데이터베이스(RDB)의 테이블을 자동으로 연결해 주는 기술

- JPA
    - Java Persistence API
    - 자바에서 사용하는 ORM(Object-Relational Mapping) 기술 표준

### 핵심 차이

> **라이브러리 = 내가 라이브러리를 호출한다.**  
> **프레임워크 = 프레임워크가 내 코드를 호출한다.**

## 1. 미션 소개
테이블 설계부터 시작해서, 요구사항을 SQL 쿼리 하나로 해결하는 흐름을 직접 완성합니다.

백엔드 프레임워크 없이, 도메인에 맞는 테이블 구조를 설계하고 전체 흐름을 실습합니다.

## 2. 최종 결과물

### 도메인 데이터베이스 1개 설계
- 자유 주제를 정하고 최소 4개 테이블을 만든다.
- 테이블 간 1:N 관계가 최소 2개 이상 포함되어야 한다.

### 스키마 생성 스크립트 1개
- CREATE TABLE로 스키마를 정의하고, PK/FK/제약조건을 포함한다.
- 실행 순서대로 정리된 .sql 파일 1개로 제출 가능해야 한다.

### 샘플 데이터 입력 스크립트 1개
- 각 테이블에 의미 있는 샘플 데이터가 들어가도록 INSERT를 작성한다.
- 각 테이블당 최소 10행 이상 데이터가 존재해야 한다.

### 핵심 쿼리 15개 + 실행 결과 캡처
- 조회/조인/집계/서브쿼리/수정 및 삭제까지 포함한 쿼리 15개를 작성한다.
- 각 쿼리의 실행 결과를 스크린샷(또는 결과 텍스트)로 남긴다.

## 3. 과제 목표
- 데이터베이스가 “엑셀과 뭐가 다른지”, 왜 테이블로 나눠 저장하는지 설명할 수 있다.
- PK/FK가 무엇이고, 1:N 관계가 데이터를 어떻게 연결하는지 말로 설명할 수 있다.
- SELECT / INSERT / UPDATE / DELETE를 언제 쓰는지 구분할 수 있다.
- JOIN과 GROUP BY로 “연결된 데이터를 한 번에 뽑는 방법”을 설명할 수 있다.
- 실무에서 흔한 요구(검색/정렬/집계/랭킹)를 SQL로 어떻게 풀지 감을 잡을 수 있다.
- 인덱스가 왜 필요한지, 어떤 컬럼에 적용하면 좋은지 기초적인 이해를 할 수 있다.

### 파일 vs 엑셀 vs DB
- 파일 -> 관리 꽥
- 엑셀 -> 좀 더 체계적이라 파일보단 편하지만 문제점들이 많음.
- DB -> 파일의 문제점들을 보완

### PK vs FK
- FK는 일반적으로 PK를 가리킴
- UNIQUE 제약 조건이 걸린 컬럼을 가리킬 수 있음.

### 1:N
- FK가 보통 여러 개임

### CRUD
- SELECT : 정보를 만들자
- INSERT : 데이터를 틀에 넣자
- UPDATE : 데이터를 변경하자
- DELETE : 데이터 삭제

### JOIN과 GROUP BY
- 뭘 말하고 싶은건지 모르겠음.
- 아예 다른 문법

### 실무에서 흔한 요구
- 해봐야 알 듯

### 인덱스
- 책갈피라 생각하기
- 보통 PK
- 많이 쓰는 컬럼

## 4. 기능 요구 사항

### 1. DB 환경 준비
- 로컬에서 실행 가능한 DB를 설치/준비한다.
- DB에 접속해 SQL을 실행할 수 있는 도구를 준비한다.
- DB별 문법 차이(날짜 함수, 자동 증가 키 등)가 존재하므로, 가급적 표준 SQL 범위 내에서 작성을 권장한다. DB 고유 문법을 사용한 경우, 해당 쿼리에 어떤 DB 전용 문법인지 주석으로 명시한다.

### 2. 데이터 모델(스키마) 설계
- 최소 4개 테이블을 설계한다.
- 각 테이블은 PK를 가진다.
- 최소 2개 이상의 FK를 사용해 1:N 관계를 만든다.
- 컬럼 타입을 의미에 맞게 선택한다. (TEXT/VARCHAR, INTEGER, DATE/DATETIME 등)
- 테이블/컬럼 이름은 역할이 드러나도록 작성한다. (member, rental, created_at 등)
- "서비스 주제(데이터 종류)"는 학습자가 직접 정하되, 최소 4개 테이블과 2개 이상의 1:N 관계를 포함할 수 있는 수준으로 선택한다.

### 3. 제약조건 적용
- 최소 1개 컬럼에 NOT NULL을 적용한다.
- 최소 1개 컬럼에 UNIQUE를 적용한다.
- FK가 실제로 동작하도록 설정한다. (없는 값 참조가 막혀야 한다)

### 4. 샘플 데이터 준비
- 각 테이블에 최소 10행 이상의 데이터를 입력한다.
- FK로 연결된 데이터가 실제로 관계를 갖도록 입력한다.
- 데이터 입력 시, FK가 참조하는 부모 테이블에 데이터가 먼저 존재해야 한다. 

### 5. 핵심 SQL 쿼리 15개 작성
- 기본 조회 4개 이상 (WHERE, ORDER BY, LIMIT 포함)
- 조인 4개 이상 (INNER JOIN 2개 이상, LEFT JOIN 1개 이상 포함)
- 집계 3개 이상 (COUNT, SUM, AVG 중 2개 이상 + GROUP BY)
- 서브쿼리 1개 이상
- 데이터 수정 및 삭제 2개 이상 (UPDATE, DELETE)
- 인덱스 1개 이상 (CREATE INDEX + 적용 이유 1줄)

### 6. 결과 확인 자료
- 쿼리마다 실행 결과를 확인할 수 있어야 한다.
- 각 쿼리에는 “무엇을 확인하는 쿼리인지” 한 줄 설명을 붙인다.
- 결과 확인은 스크린샷 또는 결과 텍스트로 남긴다.

### 7. 제출물 구성
- 스키마 생성 SQL 1개 파일
- 샘플 데이터 INSERT SQL 1개 파일
- 쿼리 15개 SQL 1개 파일
- 실행 결과 캡처(이미지 또는 텍스트) 폴더 1개
- (선택) ERD 다이어그램 이미지 1개 (draw.io, dbdiagram.io 등 활용)

## 5. 보너스 과제

### 조인 vs 서브 쿼리
- 같은 요구를 JOIN으로도 풀고, 서브쿼리로도 풀어보고 차이를 비교해본다.

### 데이터 정합성 깨뜨려 보기
- 일부러 FK 에러가 나는 입력을 시도하고, 왜 막히는지와 어떻게 고쳐야 하는지 기록해본다.

### 미니 리포트 만들기
- "이 DB로 뽑을 수 있는 핵심 지표 3개"를 정의하고, 각각을 구하는 SQL을 최종본으로 정리한다.
- 예: 월별 대여 건수 추이, 가장 인기 있는 도서 TOP 10, 연체율이 높은 회원 목록 등

## 6. 개발 환경
- 로컬에서 실행 가능한 DB를 설치/준비한다.
- DB에 접속해 SQL을 실행할 수 있는 도구를 준비한다. -> CLI 및 SQLite viewer 선택

### DB 선택 기준
- MySQL 시도 -> 내부 권한 없음. (실패) -> 도커로 가능했을지도
- SQLite 시도 -> 설치 되어 있었음

### DB에 접속해 SQL을 실행할 수 있는 도구
- CLI -> 기본적으로 가능
- SQLite Viewer -> vscode로 쉽게 다운로드 가능


## 7. 제약 사항

### 제약 사항
백엔드 프레임워크 사용 금지: Spring/Django/Express 등으로 API나 화면을 만들지 않는다.
- DB: 로컬에서 실행 가능한 DB만 사용한다.
- 범위:
    - 뷰(View), 프로시저, 트리거 같은 고급 기능은 사용하지 않는다.
    - 정규화 이론을 과도하게 깊게 파지 않는다. 대신 “관계가 자연스럽고 쿼리가 잘 나오는 구조”를 목표로 한다.
- 제출물:
    - 스키마 생성 SQL 1개 파일
    - 샘플 데이터 INSERT SQL 1개 파일
    - 쿼리 15개 SQL 1개 파일
    - 실행 결과 캡처(이미지 또는 텍스트) 폴더 1개
    - (선택) ERD 다이어그램 이미지 1개

### 제약 사항 해석

#### Q. 왜 백엔드 프레임 워크를 쓰지 말라 했을까?
A. 사실 같은 작업은 해야하나, 다음과 같은 추가 작업들이 들어감.
```
1. HTTP 요청을 처리하는 Controller 작성

2. 비즈니스 로직을 처리하는 Service 작성

3. DB에 접근하는 Repository 작성

4. SQL 또는 데이터 접근 코드를 작성

5. API 응답 형식과 오류 처리 구현
```

#### Q. 왜 로컬에서 실행 가능한 DB만 사용할까?
A. 네트워크 작업을 이해할 필요가 없음.

#### Q. 뷰(View), 프로시저, 트리거 및 정규화 이론 왜 패스?
A. DB 기초 공부하는 게 목적
